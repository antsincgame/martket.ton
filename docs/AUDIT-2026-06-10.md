Дата: 2026-06-10. Метод: пять параллельных агентов-аудиторов (фронтенд; backend-коммерция/on-chain; backend-платформа; Tact-контракты; инфраструктура/CI) + ручная верификация ключевых находок по исходникам. Известные пункты `SECURITY_TODO.md` (2026-06-09) исключены — кроме случаев, где их оценка **уточнена** (помечено «переоценка»). Находки, перепроверенные вручную построчно, помечены ✓.

Итог: **3 критических** (2 новых + 1 переоценка известного), **9 высоких**, **~20 средних**, **~20 низких**. Самое важное: on-chain доставка лицензий не работает в принципе (K-1), комиссия платформы обнуляема продавцом (K-2), а известный CON-01 на деле позволяет кражу, а не только griefing (K-3).

## Часть 1. Карта проектов

### 1.1. Фронтенд (корень + `src/`, ~175 файлов)
React 18 + Vite 5 + TS strict + Tailwind; React Router v6; TanStack Query (точечно); Appwrite Web SDK (auth + публичный каталог); TON Connect + `@ton/core` (BOC-пейлоады). Статический SPA за nginx (`deploy/nginx-spa.conf`), `/api/*` проксируется на Express.

- Вход: `index.html` (meta-CSP) → `src/main.tsx` → `src/App.tsx` (роуты, lazy-страницы, стек провайдеров Query→Auth→Network→Toast→Search→Router). `TonConnectWrapper` оборачивает только кошельковые роуты.
- `lib/` — клиенты API: `appwriteAuth.ts` (email OTP, GitHub OAuth, кэш JWT ~12 мин — Bearer для бэкенда), `storeApi.ts` (legacy `/api/...`), `commerceApi.ts` (`/api/v1/commerce/...` + заголовок `X-Ton-Network`), `distributionApi.ts`/`storageApi.ts` (BYOS), `logger.ts`, `sentry.ts`.
- `contexts/` — `AuthContext` (Appwrite-сессия → `/api/session/profile` → роли), `NetworkContext` (mainnet/testnet в `localStorage.ton_network`), `SearchContext`.
- `domain/marketplace/` — публичный каталог: Appwrite `marketplace.products/categories/reviews` + жёстко зашитый `seed.ts` (21 товар); `domain/commerce|tonforge/` — типы заказов/эскроу/лицензий.
- `pages/demiurge/` — кабинет: Overview, Library/Arsenal (`MyLicensesPanel` — on-chain confirm/burn/refund), Studio (создание/публикация + поллинг VirusTotal), Commerce (листинги/заказы/публикация/BYOS/API-токены), Wallet (привязка адреса), Profile; `admin/` — 15 вкладок по ролям.
- Три канала к бэкенду: (1) Appwrite SDK напрямую; (2) legacy REST `/api/...`; (3) commerce REST `/api/v1/commerce/...`. Платёж: `POST /orders` → `tonConnectUI.sendTransaction` → `POST /orders/:id/confirm` → поллинг `/orders/:id` до `paid` + `deliveryPayload`. Клиентские пейлоады `ConfirmDelivery` (0x45dfb5a1) и `BuyerBurn` (0x7a1b3c5d) сверены с контрактами — совпадают.

### 1.2. Бэкенд (`backend/`, ~183 файла) — Express/TS
Boot (`server.ts`): dotenv → `trust proxy 1` → requestId → logger → helmet (CSP в prod) → CORS → rate-limiters (по `req.ip`) → `express.json` (исключение только для Resend-вебхука) → sanitize → originGuard → роуты → `start()`: Sentry, опциональные роутеры (`/api/og`, `/api/v1/commerce`, `/api/v1/agent`, `/api/admin/resend`, `/api/r2`), bootstrapTonForge, cron/воркеры, listen. Graceful shutdown по SIGTERM/SIGINT.

- Воркеры: TTL-свип заказов (10 мин), scan-worker VirusTotal (15 с), commerce-реконсайлер + tonforge mint-worker (30 с, `runAllCyclesSequential`: mint → refund → payout), обновление санкционного списка.
- Авторизация по уровням: публичные (health, каталог, OG, manual); user JWT (`/api/session/*`, commerce-мутации + `requireWalletOwner`); admin/moderator (роль); super-admin; agent-токен `tfa_` (`/api/v1/agent/*`, sha256 + constant-time); `COMMERCE_ADMIN_SECRET` (commerce-админка); вебхуки со своей подписью (Resend/svix, Didit/HMAC); `X-Health-Token`.
- Денежные потоки: `POST /orders` (санкции → Lite-KYC → AML → `computeOrderAmounts` bigint → `computeEscrow` детерминированный адрес) → `confirm` (`verifyPaymentToEscrow` + `ensureLicenseForOrder` → `mint_pending`) → mint-worker (оракул WalletV4 c `ORACLE_MNEMONIC`, поллинг деплоя и саморегистрации `pollLicenseRegistered`) → `reconcileOrderAfterMint` → entitlement → download-gate (license `minted` + entitlement + скан) → 302 на presigned URL. Refund: pre-mint `RefundIfNotMinted` (подписывает покупатель), post-mint `BuyerBurn`. Payout: `timeoutRelease` после трайала с ре-скринингом продавца.
- Интеграции: Appwrite (service key), R2 + BYOS S3, Resend, TonAPI/Toncenter, VirusTotal, Didit KYC, AMLBot, прайс-оракулы (CoinGecko→Binance), Sentry.

### 1.3. Контракты (`contracts/`, Tact)
- **Escrow** — кастодиан средств одного заказа; стейт-машина `INIT(0)→FUNDED(1)→RELEASED(3)|REFUNDED(4)` (терминальные — self-destruct). Приёмники: `PayEscrow` (buyer), `ConfirmDelivery` (buyer), `RegisterLicense` (sender==licenseAddress — CON-01), `RefundOnBurn` (licenseAddress), `RefundIfNotMinted` (buyer, после grace 600 c), `TimeoutRelease` (кто угодно, после trialWindow). Release: продавцу ровно `sellerAmountNano`, treasury — остаток; refund: покупателю **весь** баланс.
- **AppCollection** — TEP-62 коллекция, минт только owner (оракул); `MintLicense` деплоит LicenseItem c `SendRemainingValue` и телом `"License minted".asComment()`; `BurnLicense`, `ChangeOwner`; `get_nft_address_by_index` — заглушка `newAddress(0,0)` (известный TEP-62).
- **LicenseItem** — soulbound TEP-62/64 NFT с `escrowAddress`; пустой `receive()` (задуман как self-register — см. K-1), `Transfer` (лимитирован), `Burn` (коллекция), `BuyerBurn` (owner, до `burnDeadline` → `RefundOnBurn` в эскроу + self-destruct), `GetStaticData`, геттеры.
- Деплой: `deployCollection.ts` (корректен, autogen-обёртка), `deploy.ts` (устаревший — см. M-15). Ручные `src/*Wrapper.ts` бэкендом не используются (у него своё зеркало `backend/tonforge/onchain/contractSchemas.ts`).
- Тесты (4 spec): happy-path и проверки доступа покрыты, но саморегистрация тестируется **подменённым** пустым телом вместо реального комментария, кросс-контрактные refund-пути застаблены, а один тест кодифицирует CON-01 как корректное поведение (см. «Ложная уверенность тестов»).

### 1.4. MCP-сервер (`mcp-server/`)
Публикуемый npm-пакет `tonforge-agent-mcp`: 13 продавцовых инструментов + 3 публичных поверх Agent API, stdio. Токен только из env, не логируется; все входы под zod; пути сверены с бэкендом — совпадают. Дефектов не найдено (нит: нет таймаута fetch).

### 1.5. Инфраструктура
- **Деплой**: Coolify → `docker-compose.yml`: `web` (Node 22 build → nginx:1.27-alpine, 8092→80) + `api` (Node 22, non-root `node`, `node --import tsx server.ts`, 8093→8081, healthcheck). Секреты — только env Coolify, в образах нет. Контракты деплоятся вручную.
- **CI**: `ci.yml` (lint/typecheck/vitest + Tact build/tests + Vite build + агрегатный гейт), `e2e.yml` (Playwright, защищён от форков), CodeQL, gitleaks, npm audit, Dependabot.
- **Скрипты**: провижининг Appwrite (4 шт.), `harden-permissions.mjs` (ремедиация §1.1 — см. M-1/M-2), ops-однострочники.
- Sweep на секреты в git — **чисто**; `.gitignore` покрывает `.env*`; e2e — только localhost.

## Часть 2. Реестр дефектов

### КРИТИЧЕСКИЕ

**K-1 ✓ [контракты] Минт лицензии не работает вовсе: `"License minted".asComment()` не матчится пустым `receive()` — деплой айтема абортится.**
`appCollection.tact:78` шлёт новому айтему текстовый комментарий (`.asComment()` = opcode `0x00000000` + текст). Единственный приёмник `licenseItem.tact:94` — пустой `receive()`, который в Tact срабатывает **только на полностью пустое тело**; текстовые комментарии маршрутизируются в `receive("…")`/`receive(msg: String)`, которых нет, fallback `receive(msg: Slice)` тоже нет → exit code 130 → **транзакция деплоя айтема абортится целиком**, аккаунт остаётся неинициализированным. Комментарий в коде (`licenseItem.tact:95-96`: «комментарий это внутреннее слово без opcode») — ошибочен. Следствия: NFT никогда не минтится; `is_registered` навсегда false; `pollLicenseRegistered` на бэке никогда не подтверждается → download не открывается; `RefundIfNotMinted` доступен покупателю всегда. Вся on-chain доставка мертва (на проде не проявилось лишь потому, что commerce выключен по env, §1.3 SECURITY_TODO). *Фикс:* реализовать регистрацию через коллекцию (план уже описан в SECURITY_TODO §2.1: `MintLicense` шлёт `RegisterLicense{licenseAddress: itemAddress}` в эскроу), удалить мёртвый self-register; деплой-сообщение слать с пустым телом или добавить `receive("License minted")`.

**K-2 ✓ [backend] Комиссия платформы подконтрольна продавцу — обнуляется до 0.**
`commerce/validation.ts:41` принимает `platformFeeBps: 0..10000` из тела запроса; `listingRoutes.ts:112,143` и `agent/routes.ts:318,350` пишут в листинг как есть; `orderRoutes.ts:104` доверяет значению листинга (дефолт 500 — только если поле отсутствует). Любой продавец (в т.ч. через Agent API) ставит `platformFeeBps: 0` — эскроу деплоится с `feeNano = 0`, treasury не получает ничего. *Фикс:* игнорировать клиентское значение либо клампить снизу к `DEFAULT_PLATFORM_FEE_BPS` на create/patch и на создании заказа.

**K-3 [контракты, переоценка CON-01] Фронт-ран `RegisterLicense` — это кража, а не «griefing/DoS».**
`escrow.tact:143-148`: регистрация фейкового контракта на FUNDED-эскроу блокирует **оба** пути возврата покупателя — `RefundOnBurn` (sender ≠ licenseAddress) и `RefundIfNotMinted` (требует `licenseAddress==0`). После `trialWindow` кто угодно (включая продавца) вызывает `TimeoutRelease` → деньги уходят продавцу. Продавец, не поставивший товар, забирает оплату; SECURITY_TODO §2.1 квалифицирует это как griefing — оценку нужно поднять. *Фикс:* тот же, что в §2.1 (`require(sender() == self.collectionAddress)` + relay из коллекции), совместить с K-1.

### ВЫСОКИЕ

**H-1 [контракты] `BuyerBurn` самоуничтожается до подтверждения рефанда.**
`licenseItem.tact:158-177`: `RefundOnBurn` уходит с `bounce:false`, `bounced()`-обработчиков нет, и в той же транзакции айтем шлёт себе `SendRemainingBalance|SendDestroyIfZero`. Если эскроу отверг `RefundOnBurn` (сегодня — всегда, по K-1; в общем случае — при не-FUNDED или несовпадении адреса), покупатель теряет и NFT, и возврат; эскроу затем уходит продавцу по таймауту. *Фикс:* не уничтожать айтем до подтверждения от эскроу (burn-confirm) либо bounceable-отправка + `bounced()` с восстановлением.

**H-2 ✓ [backend] Didit KYC-вебхук: HMAC считается по распарсенному объекту.**
`server.ts:166-168` исключает из глобального `express.json` только путь Resend; Didit-путь `/api/v1/commerce/sellers/kyc/webhook` парсится глобально, маршрутный `express.raw` (`listingRoutes.ts:331`) видит уже прочитанное тело, и `requireValidDiditSignature` (`listingRoutes.ts:314`) HMAC-ит строку `"[object Object]"`. Легитимные вебхуки **всегда 401** (KYC не авто-завершается, поллинг-фолбэка нет); подпись не привязана к содержимому — при утечке `DIDIT_WEBHOOK_SECRET` подделывается одной предвычисленной подписью для любого кошелька. *Фикс:* одна строка — добавить Didit-путь в исключение парсера в `server.ts:167`.

**H-3 [backend] Сериализация seqno оракула неполна.**
Фикс `3be9bae` сериализует циклы только внутри одного вызова `runAllCyclesSequential` (`tonforge/mintWorker.ts:457-469`). Остались: (1) `ensureLicenseForOrder.ts:96` дёргает `triggerMintLoop()` на каждый confirm, а тот гарда против payout-цикла не имеет — локи разные (`'mint-cycle'` :369 vs `'payout-cycle'` :436) → on-demand mint гонится с `timeoutRelease` на той же реплике; (2) между репликами разные локи берутся параллельно. Две внешние msg с одним seqno → одна молча теряется (минт или выплата зависает, газ сожжён). *Фикс:* единый кластерный лок `'oracle-wallet'` вокруг **каждой** отправки от оракула.

**H-4 [backend] `verifyEscrowFunded` написан, но не вызывается — минт без проверки FUNDED.**
`escrow.ts:263` (читает on-chain `state==1`) не имеет ни одного вызова вне тестов. Гейт confirm — только `verifyPaymentToEscrow` (`tonVerify.ts:232`: любой входящий от покупателя с `value ≥ total`, без opcode/состояния). Транзакция, не доведшая эскроу до FUNDED, всё равно порождает `mint_pending` → оракул минтит реальный NFT, а эскроу никогда не выплатит продавцу. *Фикс:* требовать `verifyEscrowFunded()==FUNDED` перед созданием license (в confirm или в начале `processOne`).

**H-5 ✓ [frontend] Двойной `/api`: весь commerce-фронт получает 404 при документированной конфигурации.**
`commerceApi.ts:13-21` строит `${VITE_COMMERCE_API_URL}/api/v1/commerce/...` без дедупа (в отличие от `storeApi.ts:10-12`), а во всех трёх конфигах (`.env.example:4`, `docker-compose.yml:10`, `deploy/coolify.env.example:9`) задано `VITE_COMMERCE_API_URL=/api` → запросы идут на `/api/api/v1/commerce/...`. Чекаут, листинги, лицензии, рефанды, BYOS, токены — всё мертво, при живом legacy `/api/session/*`. *Фикс:* однострочный дедуп `endsWith('/api')` в `commerceBaseUrl()`.

**H-6 [frontend] Оплата прошла, confirm упал → повторная покупка создаёт второй заказ и второй платёж.**
`CommerceCheckout.tsx:123-166`: после успешного `sendTransaction` сбой `confirmCommerceOrder` ведёт в `phase='error'`, и единственная кнопка — Buy, который заново `createCommerceOrder` → новый эскроу → пользователь платит дважды (первый платёж висит до on-chain grace-рефанда). *Фикс:* хранить `order` в стейте и при ретрае повторять только confirm/поллинг существующего `orderId`.

**H-7 [frontend] OAuth-секрет и PII в прод-логах.**
`AuthCallbackPage.tsx:27-31` логирует `window.location.href` с `?userId=...&secret=...` (живой токен обмена сессии) через `logger.warn` (в prod — консоль + Sentry-путь, `logger.ts:39-47`); семейство `[AUTH_AUDIT]` пишет email/ID в проде (`appwriteAuth.ts:142`, `AuthContext.tsx:81-144`). Бэкенд-чистку логов (`8e323b4`) фронт ре-интродьюсит. *Фикс:* логировать только `secretLen`, `[AUTH_AUDIT]` — под `import.meta.env.DEV`.

**H-8 ✓ [frontend/backend] Привязка кошелька без `ton_proof` — захват identity продавца.**
`WalletSection.tsx:20-44` PATCH-ит `{ ton_address }` без доказательства владения; `tonProof`/`setConnectRequestParameters` в репозитории отсутствуют полностью (проверено grep). `ton_address` — ключ к заказам продавца, лицензиям, выплатам и KYC-биндингу; враждебный залогиненный пользователь может заявить чужой кошелёк. *Фикс:* запрашивать `tonProof` в TonConnect и верифицировать подпись на бэке до принятия `ton_address`.

**H-9 [frontend] Опубликованные продукты продавцов не попадают в витрину — продажа невозможна.**
Витрина читает только Appwrite `marketplace.products` + сид (`marketplaceRemote.ts:69-112`); продукты Studio живут в `core.legacy_products`, синка нет (бэкенд никогда не пишет в `marketplace.products`). После всего конвейера Studio → скан → модерация → publish → авто-листинг у товара нет публичной страницы, а `CommerceCheckout` монтируется только с `ProductPage`. Тот же корень ломает «Preview» модератора (`ProductModerationQueue.tsx:274-282` → 404). *Фикс:* подтягивать опубликованные продукты из `/api/products` в `marketplaceRemote` либо серверный синк legacy→catalog.

### СРЕДНИЕ

**M-1 [infra] `harden-permissions.mjs` пропускает коллекцию `purchases`.** Создаётся с `Permission.read(Role.users())` (`provision-demiurge.mjs:59-64`) — любой залогиненный читает чужие покупки (`user_id`, `tx_hash`, `price_usd`). Бэкенд ходит туда только сервисным ключом, фронт напрямую не читает — можно безопасно закрыть. *Фикс:* добавить в `COLLECTION_TARGETS` (`harden-permissions.mjs:29-37`).

**M-2 [infra] `harden-permissions.mjs` всегда выходит с кодом 0.** Каждый сбой — `console.warn(...FAILED...)` и продолжение; счётчика и `process.exit(1)` нет (`harden-permissions.mjs:53-73`). Оператор увидит «Готово» даже при полном провале ремедиации §1.1. *Фикс:* считать сбои и выходить ненулевым кодом.

**M-3 [backend] SSRF TOCTOU в BYOS (DNS-rebinding), несмотря на новый DNS-чек.** `storageService.ts:66-92` валидирует IP через `dns.lookup`, но S3-клиент потом **резолвит заново** (`probeBucket` :112-133, и `devClient` при использовании). Хост с низким TTL отвечает публичным IP на проверке и `169.254.169.254` на запросе. Слепой SSRF (утечка топологии по reachability). *Фикс:* резолвить однажды и пиновать IP (кастомный `lookup` у клиента).

**M-4 [backend] Бан пользователя не отключает его Agent API-токены.** `is_active=false` — «единая точка бана» (`middleware/auth.ts:133`), но `agent/agentAuth.ts:106-199` профиль не загружает и `is_active` не проверяет. Забаненный продавец сохраняет полный Agent API, пока KYC approved и токен не отозван. *Фикс:* в `apiRequireAgentToken` резолвить профиль по кошельку и отклонять `isActive===false`.

**M-5 [backend] Email — merge-ключ профиля без проверки `emailVerification`.** `auth.ts:113-127` → `upsertProfileForAppwriteUser` (`profileRepository.ts:182-205`) находит профиль **по email** и перезаписывает `appwrite_user_id`. Если какой-либо auth-метод даёт JWT с неверифицированным email — захват чужого профиля (`ton_address`, роль, покупки) первым же запросом. *Фикс:* merge по email только при `emailVerification===true`.

**M-6 [backend] v4-confirm не идемпотентен для ledger.** Заказ остаётся `pending_payment`, гард `orderRoutes.ts:239` не срабатывает, и каждый повторный confirm пишет новый `escrow_fund` (`orderRoutes.ts:315-329`; `recordLedgerEntry` без дедупа). Покупатель может накачать compliance-ledger дубликатами. *Фикс:* дедуп по `(refType, refId, entryType)` либо запись только при первом проставлении `tonTxHash`.

**M-7 [backend] Commerce-реконсайлер доверяет `license_address` эскроу без сверки — митигация CON-01 неполна.** `pollLicenseRegistered` сверяет ожидаемый адрес только в tonforge-воркере; `commerce/mintWorker.ts:184-224` финализирует на **любом** ненулевом `license_address` и пишет его в entitlement/ledger. После фронт-рана CON-01 заказ помечается `paid` с адресом атакующего. *Фикс:* финализировать только при совпадении с `nftAddress` из `licenses`.

**M-8 [backend] Скан-гейт advisory — продавец может перепубликовать незсканированный билд.** Download-gate блокирует только `malicious|suspicious` (`downloadGate.ts:46`); `PUT …/distribution` сбрасывает `scan_status:'idle'` (`distributionRoutes.ts:185`, `agent/routes.ts:473`), `verify` сверяет **продавцовский** sha256 и не пере-сканирует.
